# Claude Code JSONL Compact Summary 编辑与校验工具分析

## 一、需求理解

目标不是简单做一个 JSON 美化器，而是做一个面向 Claude Code Transcript 的安全编辑器：

1. 用户粘贴一整条 JSONL 记录，或者以后导入整个 `.jsonl` 会话文件。
2. 应用解析该记录并提取 `/message/content`。
3. 把 JSON 字符串里的 `\n`、`\"`、`\\` 等转义还原成可编辑的多行文本。
4. 用接近 Claude Code Transcript 的布局预览内容。
5. 用户只修改 `message.content`，其他 UUID、父子关系、时间戳和未知字段默认锁定。
6. 分别验证 Content、整条记录和最终单行 JSONL。
7. 将修改后的多行文本安全序列化回一条 JSONL 记录。
8. 证明输出再次解析后得到的 Content 与用户编辑结果完全一致，并证明其他字段没有被改变。

这个方向是可行的。第一版最合适的输入不是只粘贴 Content，也不是直接加载 70 MB 的完整会话文件，而是粘贴**第 8555 行的整条 JSON 记录**。这样既能编辑正文，又能原样保留该消息的所有元数据。

本文中的目标记录来自：

```text
/Users/admin/.claude/projects/-Volumes-zhitai-7100-zhihu-zhida-api/7d14919c-8e0e-4d63-b263-dad4bc0ab5d0.jsonl
```

当前文件约 70 MB，第 8555 行约 11.8 KB。单行导入适合作为 MVP；整个文件导入可以作为第二阶段能力。

## 二、首先澄清：“一行 Content”实际上有两个层次

编辑器中看到的第 8555 行是一个物理单行：

```jsonl
{"message":{"content":"first line\nsecond line\n\"quoted\""}}
```

这里的 `message.content` 在 JSON 源文本里使用转义序列，所以不会真的换行。经过 `JSON.parse()` 后，它变成正常的 JavaScript 多行字符串：

```text
first line
second line
"quoted"
```

修改完成后调用 `JSON.stringify()`，真实换行会重新变成 `\n`，双引号会变成 `\"`，反斜杠会变成 `\\`。因此不应该自己编写字符串替换规则，也不应该手工“压缩”换行。

正确的基本关系是：

```text
JSONL 单行源文本
    -> JSON.parse / JSON AST
JavaScript 多行 content 字符串
    -> 用户编辑
修改后的多行字符串
    -> JSON.stringify 或 AST 定点替换
新的 JSONL 单行源文本
```

建议在产品文案中把“压缩”按钮命名为：

```text
生成单行 JSONL
```

不要叫“Compact”或“压缩”，否则容易与 Claude Code 的上下文 Compact 混淆。

## 三、Claude Code 是如何生成这段 Content 的

### 3.1 Compact 模型生成九段式摘要

[`src/services/compact/prompt.ts`](../src/services/compact/prompt.ts) 中的 `BASE_COMPACT_PROMPT` 要求摘要包含：

1. Primary Request and Intent
2. Key Technical Concepts
3. Files and Code Sections
4. Errors and fixes
5. Problem Solving
6. All user messages
7. Pending Tasks
8. Current Work
9. Optional Next Step

模型最初被要求输出：

```text
<analysis>
草稿分析
</analysis>

<summary>
九段式摘要
</summary>
```

### 3.2 源码清理模型输出

[`formatCompactSummary()`](../src/services/compact/prompt.ts#L311) 做三件事：

1. 删除 `<analysis>...</analysis>` 草稿。
2. 将 `<summary>...</summary>` 替换成可读的 `Summary:\n...`。
3. 合并多余空行并执行 `trim()`。

所以 JSONL 中看见的 `Summary:` 不是网页或终端 Markdown 渲染器生成的，而是 Compact 后处理代码写入 Content 的普通文本。

### 3.3 源码增加续接前缀和 Transcript 路径

[`getCompactUserSummaryMessage()`](../src/services/compact/prompt.ts#L337) 在摘要前面添加固定前缀：

```text
This session is being continued from a previous conversation that ran out of context. The summary below covers the earlier portion of the conversation.
```

随后追加格式化后的 `Summary:`，并在有会话路径时追加：

```text
If you need specific details from before compaction ... read the full transcript at: <path>
```

因此第 8555 行的 Content 是：

```text
固定续接前缀
+ formatCompactSummary() 的结果
+ Transcript 路径提示
+ 某些模式下的继续执行指令
```

九个章节是一种由 Compact prompt 约定的内容结构，不是 JSONL 解析器强制的语法。

## 四、Content 如何渲染成 `Compact summary` 和 `⎿`

### 4.1 消息类型分流

[`src/components/Message.tsx`](../src/components/Message.tsx#L157) 处理 user 消息时检查：

```ts
if (message.isCompactSummary) {
  return <CompactSummary message={message} ... />
}
```

所以决定使用特殊 Summary UI 的是顶层字段：

```json
"isCompactSummary": true
```

不是 Content 以 `This session...` 开头这一事实。

### 4.2 提取 Content

[`getUserMessageText()`](../src/utils/messages.ts#L2861) 调用 `getContentText()`：

```ts
if (typeof content === 'string') {
  return content
}
```

第 8555 行的 Content 本来就是字符串，所以源码没有再次解析 Markdown、XML 或章节字段，只是直接取得字符串。

### 4.3 绘制标题

[`src/components/CompactSummary.tsx`](../src/components/CompactSummary.tsx#L14) 在没有 partial-compact metadata 时绘制粗体标题：

```tsx
<Text bold={true}>Compact summary</Text>
```

`Compact summary` 这几个字**不在** `message.content` 内，也不应该被网页编辑器写回 Content。

### 4.4 绘制 `⎿` 前缀

同一个组件在 Transcript 模式下执行：

```tsx
<MessageResponse>
  <Text>{textContent}</Text>
</MessageResponse>
```

[`src/components/MessageResponse.tsx`](../src/components/MessageResponse.tsx#L10) 另外绘制：

```tsx
<Text dimColor={true}>{"  "}⎿  </Text>
```

所以 `⎿`、其前面的两个空格以及后面的间隔也都是 UI 外框，不属于 Content。

### 4.5 换行和自动折行

`textContent` 被放进 Ink 的 `<Text>` 和弹性布局 `<Box>`。最终展示由两种换行共同组成：

- Content 原本包含的 `\n` 在 `JSON.parse()` 后成为强制换行。
- 超过终端可用列宽的长行由 Ink/Yoga 按终端宽度自动折行。
- `MessageResponse` 左侧 gutter 占用一定列宽，正文使用剩余宽度。

因此示例里这类断行：

```text
verification/anti-crawler
mechanism to download ...
```

不一定在原始 Content 中真的存在换行，也可能只是终端宽度造成的视觉折行。

### 4.6 它不是 Markdown 渲染

Compact Summary 使用的是：

```tsx
<Text>{textContent}</Text>
```

不是项目中的 `<Markdown>` 组件。因此 `**粗体标记**`、反引号和三反引号在这一视图里原则上是普通字符。网页应用如果要模拟 Claude Code 的真实效果，默认应使用原样文本预览，而不是把 Markdown 渲染成 HTML。

可以额外提供“Markdown 辅助预览”标签页，但必须明确标注它不是 Claude Code 的权威渲染效果。

## 五、推荐的产品形态

### 5.1 MVP：完整单行记录模式

推荐第一版流程：

1. 粘贴第 8555 行的完整 JSON。
2. 解析并识别 `/message/content`。
3. 其他字段进入只读状态。
4. 中间编辑器只允许修改 Content。
5. 右侧实时显示 Transcript 风格预览和验证结果。
6. 点击“生成单行 JSONL”。
7. 应用完成最终解析、字段保护和 round-trip 检查。
8. 通过后才允许复制输出。

为什么不建议只粘贴 Content：

- 只粘贴 Content 后无法确认它属于哪条消息。
- 容易重新创建错误的 UUID、`parentUuid`、时间戳或标记。
- 无法证明输出相较原记录只改了一个字段。
- 无法保留未来版本增加的未知字段。

### 5.2 第二阶段：完整 JSONL 文件模式

可以增加：

1. 导入整个 `.jsonl` 文件。
2. 流式逐行解析，而不是 `split('\n')` 后一次构建全部对象。
3. 筛选 `isCompactSummary === true` 的记录。
4. 按时间、UUID 和行号选择 Summary。
5. 修改后生成一个新的完整 JSONL 文件。

当前示例文件约 70 MB，浏览器虽然通常能够处理，但不应该把所有记录同时转成庞大的对象数组。可以使用：

```text
File.stream()
-> TextDecoderStream
-> 行分割 TransformStream
-> 只为匹配记录建立索引
```

第一版没有必要承担这个复杂度。

## 六、推荐界面布局

这是一个操作型工具，建议使用紧凑、三栏或三标签布局：

### 输入区

- 完整 JSONL 单行输入框。
- “解析记录”命令。
- 显示检测到的 `uuid`、`timestamp`、`type`、`message.role` 和行长。
- 原始输入解析成功后锁定；需要更换记录时显式重置。

### Content 编辑区

- 多行等宽文本编辑器。
- 行号、字符数和换行数。
- Content diff，显示相对原始值增加、删除和修改的位置。
- 默认不允许编辑 JSON 外壳。

首版使用普通 `<textarea>` 已足够。后续若需要代码块折叠、搜索替换和大文本性能，再使用 CodeMirror。

### 预览与验证区

- 只读标题 `Compact summary`。
- 左侧只读 `⎿` gutter。
- 正文使用 `white-space: pre-wrap`。
- 提供终端列宽滑块，例如 80、100、120、160 列。
- 分开展示“错误”“警告”“信息”。

浏览器 CSS 与真实终端单元格宽度并不完全相同，尤其是中文、Emoji 和全角字符。若需要接近 Ink 的折行，可以按终端 cell width 计算；项目已经依赖 `get-east-asian-width` 和 `wrap-ansi`，可以参考其规则。普通 CSS 预览应标记为“视觉近似”。

## 七、不要重新构造整个对象，应该定点替换 Content

### 7.1 简单方案

最简单的实现是：

```ts
const original = JSON.parse(rawLine)
const edited = structuredClone(original)
edited.message.content = draftContent
const outputLine = JSON.stringify(edited)
```

对于第 8555 行可以正常工作。`JSON.parse()` 后对象的属性插入顺序通常会被 `JSON.stringify()` 保留。

### 7.2 更稳妥的推荐方案

项目根依赖已经包含 `jsonc-parser`。推荐用 JSON AST 找到 `/message/content` 的源文本范围，只替换这个 JSON 字符串字面量：

```ts
const errors = []
const tree = parseTree(rawLine, errors, {
  allowTrailingComma: false,
  disallowComments: true,
})
const contentNode = findNodeAtLocation(tree, ['message', 'content'])

const replacement = JSON.stringify(draftContent)
const outputLine =
  rawLine.slice(0, contentNode.offset) +
  replacement +
  rawLine.slice(contentNode.offset + contentNode.length)
```

这个方案的优势：

- 除 Content 值之外的原始字节完全不动。
- 不会重排键。
- 不会改变其他字符串的转义形式。
- 不会因为 JavaScript number 精度问题改写极大整数。
- 可以直接证明修改范围只有 `/message/content`。

项目源码的 Transcript 快速扫描还记录了一个重要约定：消息通常以 `{"parentUuid":...` 开头，预解析优化依赖 `parentUuid` 是第一个键。普通 JSON 语义不要求键顺序，但为了与当前实现完全兼容，工具不应排序键或重新构造对象。

## 八、三层验证体系

用户提出“先检查 Content，再检查整个 JSON，最后检查单行 JSONL”，这个顺序是正确的。建议做成三个独立 Gate。

### Gate A：Content 检查

#### 硬错误

- Content 不是字符串。
- 包含未经允许的 NUL 或危险控制字符。
- Content 超出产品设置的大小限制。
- 编辑器内部字符串无法与输出再次解析后的字符串逐 code unit 相等。

#### Compact 约定警告

- 不再以 `This session is being continued...` 开头。
- 缺少 `Summary:`。
- 九个编号章节缺失、重复或乱序。
- Markdown code fence 数量不平衡。
- Transcript 路径提示被意外删除或改成另一个会话。
- 内容为空，或者相比原文删除比例超过阈值。

这些只能是警告或“严格模式”错误，因为 Claude Code 的 JSONL 解析器并不要求 Content 必须具有九段式结构。一个任意字符串仍然是合法 Content，只是可能让后续模型失去关键上下文。

工具也无法自动判断摘要中的事实是否正确。即使所有格式检查通过，用户把某个文件名或待办事项改错，JSON 仍然完全合法，但后续 Claude 会收到错误上下文。

### Gate B：整条消息检查

针对 Compact Summary 的安全 Profile，至少检查：

```text
root                         是 object
type                         === "user"
message                      是 object
message.role                 === "user"
message.content              是 string
isCompactSummary             === true
isVisibleInTranscriptOnly    === true（针对本例）
uuid                         保持原值且格式有效
parentUuid                   保持原值
sessionId                    保持原值
timestamp                    保持原值且可解析
isSidechain                  保持类型和值
```

还应执行“受保护字段 diff”：

```text
允许变化：/message/content
禁止变化：其他所有 JSON Pointer
```

项目已经依赖 Ajv，可以为特定消息 Profile 提供 JSON Schema 校验。但 Schema 只负责类型和必填字段；“只能改 Content”仍需要原始对象与输出对象的 diff 或源范围证明。

### Gate C：最终 JSONL 检查

最终输出必须满足：

1. 除可选的文件末尾换行外，输出只有一个物理行。
2. `JSON.parse(outputLine)` 成功。
3. 解析结果是 object。
4. `parsed.message.content === draftContent`。
5. 输出重新经过相同 Schema 检查。
6. 除 `/message/content` 外没有字段发生变化。
7. `uuid`、`parentUuid` 和 `sessionId` 与原值完全相同。
8. 输出没有 BOM、前置日志、Markdown 围栏或复制提示文字。
9. 将输出作为 `line + "\n"` 交给 JSONL 逐行解析器时恰好产生一条记录。

建议最终界面给出明确证明：

```text
PASS  JSON 语法有效
PASS  单物理行
PASS  Compact Summary schema
PASS  Content round-trip 完全一致
PASS  仅 /message/content 发生变化
PASS  UUID / parentUuid / sessionId 未改变
```

只要任何硬检查失败，就禁用“复制最终 JSONL”。

## 九、Round-trip 验证应该如何实现

核心检查不是“看起来一样”，而是解析后的值完全一样：

```ts
const reparsed = JSON.parse(outputLine)

assert(reparsed.message.content === draftContent)
assert(!outputLine.includes('\n'))
assert(reparsed.uuid === original.uuid)
assert(reparsed.parentUuid === original.parentUuid)
```

注意上例中 `outputLine.includes('\n')` 检查的是实际 LF 字符，不是字符串里的两个字符 `\\n`。合法单行 JSONL 需要保留 `\\n` 转义，但不能在一条记录内部出现真实 LF。

使用 AST 定点替换时还可以做更强的字节级证明：

```text
原始 Content 节点之前的字节 === 输出 Content 节点之前的字节
原始 Content 节点之后的字节 === 输出 Content 节点之后的字节
```

这比对两个重新序列化后的对象更可靠。

## 十、为什么验证失败可能没有明显报错

[`src/utils/json.ts`](../src/utils/json.ts#L129) 中的 JSONL fallback parser 是逐行执行 `JSON.parse(line)`。如果某一行解析失败，它会 catch 后跳过 malformed line，而不是让整个文件立即崩溃。

这意味着错误编辑可能表现为：

- 该条 Summary 在恢复时悄悄消失。
- 子消息找不到 `parentUuid`，有效对话链被截断。
- Claude Code 选择了另一条 leaf 或恢复出不完整上下文。

所以“浏览器里 JSON.parse 成功”必须是阻断式检查，不能只是黄色警告。

## 十一、写回真实文件时的安全策略

网页工具第一版不应该直接覆盖 `~/.claude/projects/**/*.jsonl`。推荐：

1. Claude Code 会话运行时禁止写回。
2. 默认只生成单行结果或一个新的 patched JSONL 文件。
3. 写回前自动生成原文件备份。
4. 整文件替换应使用临时文件加原子 rename，不要在原文件中按旧字节长度原地覆盖。
5. 以 UUID 定位记录，不把行号当成永久 ID。
6. 修改后重新逐行验证整个输出文件。
7. 验证目标 UUID 恰好出现一次。
8. 验证所有非目标行的字节与原文件完全一致。

目标 Content 变长或变短会改变后续字节偏移，所以不能用简单的固定长度覆盖。整文件模式应流式复制：遇到目标 UUID 时输出新行，其他行原样输出。

## 十二、建议的数据状态

```ts
type EditorState = {
  rawLine: string
  originalTree: JsonNode | null
  originalRecord: unknown
  originalContent: string
  draftContent: string
  outputLine: string | null
  diagnostics: Diagnostic[]
  sourceFingerprint: string
}
```

`sourceFingerprint` 可以是原始行的 SHA-256，用于提示用户当前结果是从哪条原始记录派生出来的。

诊断对象建议包含：

```ts
type Diagnostic = {
  gate: 'content' | 'record' | 'jsonl'
  severity: 'error' | 'warning' | 'info'
  code: string
  message: string
  location?: { start: number; end: number }
}
```

## 十三、建议的实施阶段

### Phase 1：单行安全编辑器

- 粘贴完整 JSONL 行。
- AST 解析并提取 Content。
- Content-only 编辑。
- Transcript 风格原样预览。
- Content/Record/JSONL 三层验证。
- 精确替换并复制单行结果。
- 原文与修改后 Content diff。

### Phase 2：内容质量保护

- 九章节结构检查。
- code fence 平衡检查。
- 固定前缀和 Transcript 路径保护。
- 删除比例和敏感字段变化提示。
- 可配置严格模式。

### Phase 3：整个会话文件

- 流式导入 JSONL。
- Compact Summary 列表和搜索。
- 按 UUID 定位。
- 流式生成 patched 文件。
- 全文件逐行验证和非目标行字节一致性检查。

## 十四、最终建议

建议直接采用下面的核心产品决策：

1. **MVP 输入整条第 8555 行 JSON，而不是只输入 Content。**
2. **默认只允许编辑 `/message/content`。**
3. **使用 JSON AST 定点替换，不重建整个对象。**
4. **预览里的 `Compact summary` 和 `⎿` 由 UI 单独绘制，绝不写入 Content。**
5. **默认采用纯文本 `pre-wrap` 预览，不把 Markdown HTML 渲染当成权威结果。**
6. **执行 Content、Record、JSONL 三层 Gate。**
7. **最终必须通过 parse -> compare -> serialize/parse round-trip。**
8. **第一版只复制结果，不直接改真实会话文件。**
9. **以后处理整个 70 MB 文件时采用流式读取和流式替换。**

这个工具真正需要保证的不是“输出看起来像一行”，而是：

```text
输出是一个合法 JSONL record
+ 解析后 Content 与编辑器内容完全一致
+ 只有 Content 被修改
+ 会话链关键字段完全保留
```

满足这四点，生成的单行记录才能被当前 Claude Code JSONL 读取机制稳定识别。

## 十五、关于 `JSON.parse()` 解码 Content 的进一步核实

### 15.1 这句话是否准确

下面这句话在语义上是准确的：

> Content 通过 JSON 解析，从单行中的 `\n`、`\"`、`\\` 等 JSON 转义序列还原为包含真实换行、双引号和反斜杠的字符串。

但需要补充两个限定：

1. `JSON.parse()` 负责的是 JSON 语法解析和字符串转义解码，不负责 `Compact summary`、`⎿`、缩进或终端自动折行。
2. 当前项目运行在 Bun 时优先使用 `Bun.JSONL.parseChunk()`；fallback 路径才逐行执行 `JSON.parse(line)`。两条路径遵循相同的 JSON 字符串解码语义。

当前源码 [`src/utils/json.ts`](../src/utils/json.ts#L94) 的实际选择是：

```text
存在 Bun.JSONL.parseChunk
    -> Bun.JSONL.parseChunk(data)
否则
    -> 按 LF 拆分
    -> 对每个非空行执行 JSON.parse(line)
```

所以更严谨的表述是“通过标准 JSON 解析语义还原”，而不是断言所有运行环境一定直接调用 JavaScript 的 `JSON.parse()`。

### 15.2 到底发生了什么

JSONL 源文件中的两个字符：

```text
\n
```

在 JSON string literal 内表示一个换行字符 U+000A。类似地：

| JSON 源文本 | 解析后的字符串内容 |
| --- | --- |
| `\n` | 一个真实换行符 |
| `\r` | 一个回车符 |
| `\t` | 一个制表符 |
| `\"` | 一个普通双引号 `"` |
| `\\` | 一个普通反斜杠 `\` |
| `\u4e2d` | Unicode 字符 `中` |

反方向调用 JSON serializer 时，这些字符会重新编码成合法 JSON string literal。这个过程是标准 JSON 能力，不是 Claude Code 自己设计的特殊压缩算法。

### 15.3 Node.js、Bun 和浏览器不需要第三方库

Node.js、Bun 和浏览器都原生提供：

```ts
JSON.parse()
JSON.stringify()
```

单条记录的最小示例：

```ts
const rawLine =
  '{"message":{"content":"第一行\\n第二行\\n\\"quoted\\"\\n\\\\path"}}'

const record = JSON.parse(rawLine)

// textarea 中现在是包含真实换行的多行字符串
const editableContent = record.message.content

record.message.content = editableContent + '\n新增一行'

// outputLine 内部的真实换行会被重新编码为 \n，结果仍是一物理行
const outputLine = JSON.stringify(record)

const reparsed = JSON.parse(outputLine)
console.assert(reparsed.message.content === record.message.content)
console.assert(!outputLine.includes('\n'))
```

这里最后一个 `includes()` 检查的是实际换行字符。`outputLine` 中仍然可以、也应该包含两个普通字符组成的 `\\n` 转义序列。

### 15.4 Python 标准库同样可以完成

Python 不需要安装第三方库，内置 `json` 模块就够了：

```python
import json

raw_line = r'{"message":{"content":"第一行\n第二行\n\"quoted\"\n\\path"}}'

record = json.loads(raw_line)
editable_content = record["message"]["content"]

record["message"]["content"] = editable_content + "\n新增一行"

output_line = json.dumps(
    record,
    ensure_ascii=False,
    separators=(",", ":"),
)

reparsed = json.loads(output_line)
assert reparsed["message"]["content"] == record["message"]["content"]
assert "\n" not in output_line
```

其中：

- `ensure_ascii=False` 让中文保持为中文；使用默认值将中文编码成 `\uXXXX` 也仍是合法 JSON。
- `separators=(",", ":")` 去掉逗号和冒号后的多余空格，得到紧凑单行。
- `json.loads()` 对应 JavaScript 的 `JSON.parse()`。
- `json.dumps()` 对应 JavaScript 的 `JSON.stringify()`。

### 15.5 JSONL 与普通 JSON 的差别只在外层读取方式

对于单独的第 8555 行，可以直接：

```ts
const record = JSON.parse(line8555)
```

但不能对完整的 70 MB JSONL 文件直接执行：

```ts
JSON.parse(entireJsonlFile) // 会失败
```

因为整个文件不是一个 JSON 数组，而是多个顶层 JSON 值。正确方法是逐行解析：

```ts
for (const line of lines) {
  if (!line.trim()) continue
  const record = JSON.parse(line)
}
```

因此所谓 JSONL 库，核心也是帮助完成：

```text
读取流 -> 划分完整行 -> 每行 JSON 解析 -> 输出对象流
```

### 15.6 确实有很多可用库，但基本功能不依赖它们

| 环境 | 内置能力 | 可选库及适用场景 |
| --- | --- | --- |
| 浏览器 | `JSON.parse`、`JSON.stringify`、File/Blob API | `jsonc-parser` 用于 AST 定点替换；Ajv 用于 Schema 校验 |
| Node.js | `JSON.parse`、`JSON.stringify`、`readline`、Streams | `ndjson`、`stream-json` 等用于大型文件流式处理 |
| Bun | `JSON.parse`、`JSON.stringify`、`Bun.JSONL.parseChunk` | `jsonc-parser` 用于原始字节保留 |
| Python | `json.loads`、`json.dumps`、逐行文件迭代 | `jsonlines` 简化 JSONL 读写；`orjson` 提高大量数据序列化性能 |

对于本工具：

- 解码和重新编码 Content：浏览器原生 JSON API 足够。
- 只替换 `/message/content`：建议使用现有 `jsonc-parser`。
- 校验 Compact Summary 消息结构：建议使用现有 Ajv。
- 处理整个 70 MB 文件：再考虑浏览器 Streams 或专门 JSONL 流式库。

### 15.7 完全可以做成纯前端静态应用

这个应用不需要后端服务器。浏览器自身已经具备：

- JSON 解析和序列化；
- `<textarea>` 多行编辑；
- File API 读取用户选择的文件；
- Streams API 处理大型文件；
- Blob 和下载 API 生成 patched 文件；
- Clipboard API 复制最终单行；
- Web Crypto API 计算 SHA-256 指纹。

纯前端方案还有一个重要优势：会话内容可以只存在于本地浏览器内存，不需要上传服务器。

预览时应把 Content 放入 `<pre>`、`<textarea>` 或通过 DOM `textContent` 输出，不要直接设置 `innerHTML`。这样既能保留换行，也能避免 Content 中的 HTML 字符被浏览器当成页面代码。

### 15.8 为什么仍然推荐 AST 定点替换

`JSON.parse()` 加 `JSON.stringify()` 足以生成 Claude Code 能识别的合法单行记录，但不保证输出与原始行字节一致：

- 空格可能变化。
- Unicode 可能采用不同但等价的表示。
- 某些转义可以被规范化。
- 如果重新构造对象，键顺序可能变化。
- JavaScript 对超大 JSON number 可能发生精度损失。

这些差异通常不影响 JSON 语义，但本工具的目标更严格：只允许 Content 变化。因此仍建议：

1. 使用 JSON parser 验证和取得逻辑值。
2. 使用 JSON AST 找出 Content 在原始行中的 offset/length。
3. 只用 `JSON.stringify(draftContent)` 生成新的字符串字面量。
4. 将这个字面量替换回原始行对应范围。
5. 再次使用 `JSON.parse()` 验证最终结果。

### 15.9 最终判断

答案是肯定的：

- `\n` 等转义由标准 JSON parser 解码为真实字符。
- Node.js、Bun、Python 和浏览器都能原生完成。
- 完全可以实现为不上传数据的纯前端静态网页。
- 第三方库不是基础解析所必需，而是用于定点修改、Schema、diff 和大文件流式处理。
- 语法解析成功只能证明 JSON 合法，不能证明九段式 Summary 内容完整或事实正确；后者仍需要额外的 Content lint 和人工审查。

### 16.3 三层验证的准确含义

界面中的三个 Gate 分工如下：

| Gate | 检查内容 |
| --- | --- |
| Content | 空内容、控制字符、Compact 固定开头、`Summary:`、1 到 9 段标题、代码围栏、异常删除比例、transcript 路径等 |
| Record | 顶层消息结构、`type`、`message.role`、`message.content`、`isCompactSummary`、UUID、时间戳等 |
| JSONL | 输出可再次 `JSON.parse()`、只有一个物理行、Content 往返一致、Content 之外字段深度相等 |

普通模式下，九段式标题缺失等属于结构警告，因为 Claude Code 消费的是普通字符串，并不存在一个要求必须九段齐全的 API Schema。严格模式会把这些约定性警告提升为错误，适合修改真实 Compact Summary 时防止误删大块内容。

### 16.4 Content 是如何被替换的

应用不会对整条记录执行一次普通的 `JSON.stringify(parsedRecord)` 来生成最终结果。实际步骤是：

1. 用 `jsonc-parser` 建立原始单行的语法树。
2. 定位 `/message/content` 对应的字符串节点及其 `offset`、`length`。
3. 只对编辑后的 Content 调用 `JSON.stringify(draftContent)`。
4. 用新的 JSON 字符串字面量替换原始行中的那一段源码。
5. 重新解析最终行并进行往返和字段不变性检查。

因此在 Content 没有变化时，最终输出会与输入原始行逐字相同；Content 发生变化时，原记录的空格、键顺序、其他字符串转义和其他字段源码均不被重排。
